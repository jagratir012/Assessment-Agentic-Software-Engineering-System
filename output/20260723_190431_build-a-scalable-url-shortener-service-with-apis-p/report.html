1. Requirement Analysis

Type: Greenfield  |  Intent: Build a production-grade, scalable URL shortener microservice with REST APIs, persistent storage, and usage analytics capabilities.

Functional Requirements

  1. Accept a long URL via API and return a unique shortened URL alias
  2. Redirect users from the shortened URL to the original long URL
  3. Support custom alias creation for shortened URLs
  4. Track analytics per shortened URL including click count, timestamp, referrer, and geographic location
  5. Provide an API endpoint to retrieve analytics data for a given shortened URL
  6. Support URL expiration with configurable TTL per shortened URL
  7. Validate input URLs for proper format and reachability before shortening
  8. Support bulk URL shortening via batch API endpoint
  9. Allow deletion or deactivation of a shortened URL by authorized users
  10. Provide an API to list all shortened URLs associated with a user or account

Non-Functional Requirements

  • System must handle at least 10,000 read requests per second for redirects with sub-100ms latency
  • Shortened URL aliases must be globally unique and collision-resistant
  • Service must achieve 99.9% uptime SLA with horizontal scalability
  • All API endpoints must be secured with authentication and authorization (e.g., API keys or OAuth2)
  • Analytics data pipeline must not block or degrade redirect performance
  • Persistent storage must support data durability and replication to prevent data loss
  • The system must be deployable as independent microservices with container orchestration (e.g., Kubernetes)
  • API responses must conform to RESTful standards with proper HTTP status codes and versioning

Ambiguities Identified

  • ⚠️ The alias generation strategy is unspecified (random hash, base62 encoding, sequential ID, etc.)
  • ⚠️ The target persistence layer is not defined (SQL, NoSQL, Redis, or a combination)
  • ⚠️ Analytics granularity and retention policy are not specified (real-time vs. batch, how long data is kept)
  • ⚠️ User/account management scope is unclear — whether the service manages its own auth or integrates with an external identity provider
  • ⚠️ The expected length of shortened URL aliases is not defined
  • ⚠️ Whether the service needs a frontend/dashboard UI or is purely API-driven is unspecified
  • ⚠️ Rate limiting requirements per user or IP are not defined
  • ⚠️ Multi-tenancy requirements are not specified

Assumptions Made

  • ✅ Aliases will be 6-8 character base62-encoded strings generated from a hash or counter to ensure uniqueness
  • ✅ A combination of Redis (for caching hot redirects) and a relational database like PostgreSQL (for persistence) will be used
  • ✅ Analytics will be collected asynchronously via a message queue (e.g., Kafka or SQS) to avoid impacting redirect latency
  • ✅ Authentication will use API keys for service-to-service calls and JWT/OAuth2 for user-facing operations
  • ✅ The service is API-only with no frontend UI in scope for this phase
  • ✅ Rate limiting will be enforced at the API gateway level (e.g., 100 requests/minute per API key by default)
  • ✅ Analytics data will be retained for 90 days by default with aggregated summaries kept indefinitely
  • ✅ The system will be deployed on Kubernetes with at least 3 replicas per service for high availability

    6. Risk Assessment & Validation

    Identified Risks

    SeverityCategoryDescriptionMitigation
    CRITICALSecurityURL shorteners are a well-known vector for phishing, malware distribution, and SSRF attacks. Malicious actors can shorten harmful URLs and use the service to obfuscate destinations. Additionally, if the shortener resolves internal/private IP ranges (e.g., 10.x.x.x, 169.254.x.x), it could be exploited for SSRF to access internal services.Implement URL validation at creation time: (1) Blocklist known malicious domains via integration with Google Safe Browsing API or similar threat intelligence feeds. (2) Enforce an allowlist/denylist for destination URL schemes (only allow http/https). (3) Block resolution to RFC-1918 private IP ranges, loopback addresses, and cloud metadata endpoints (169.254.169.254) before storing. (4) Scan destination URLs asynchronously post-creation and deactivate flagged links.
    HIGHData IntegrityHash-based alias generation (e.g., MD5/SHA truncated to 6-8 chars in base62) has a non-trivial collision probability at scale. With a 6-character base62 space (~56 billion combinations), at 10% fill (~5.6B URLs) the birthday paradox gives roughly 5% collision probability per insertion, causing failed writes or silent overwrites of existing aliases.Use a distributed atomic counter (e.g., Redis INCR or a dedicated sequence in PostgreSQL) as the primary alias generation strategy rather than hashing. Reserve hash-based generation only for custom vanity aliases. Implement a collision detection loop with a maximum retry limit (e.g., 3 attempts) before returning a 503. Add a unique constraint on the alias column in PostgreSQL as the final safety net. Monitor collision rate as a key operational metric.
    HIGHAvailabilityRedis is the critical hot path for redirect latency. A Redis cluster failure or cache stampede (many simultaneous cache misses for the same key after expiry) will cause a thundering herd against PostgreSQL, potentially overwhelming the database and causing cascading failures across all redirect operations.Implement cache stampede protection using probabilistic early expiration (PER algorithm) or a mutex/lock pattern (Redis SET NX) so only one request rebuilds a cache entry while others wait briefly. Configure Redis with persistence (AOF + RDB) and use Redis Sentinel or Redis Cluster for HA. Set circuit breakers on the PostgreSQL connection pool so Redis failures degrade gracefully rather than cascading. Pre-warm cache for top-N URLs on service startup.
    MEDIUMPerformanceAsynchronous analytics via Kafka/SQS introduces a consumer lag risk. If the analytics consumer falls behind (e.g., due to a spike in traffic or consumer crash), the queue depth grows unboundedly. This can cause memory/disk exhaustion on the broker, delayed analytics reporting, and potential message loss if retention limits are hit before consumption.Set explicit Kafka topic retention policies (e.g., 48-hour retention, 10GB max per partition) as a safety valve. Configure consumer group lag alerting with thresholds (e.g., alert at >10k messages lag, page at >100k). Implement dead-letter queues (DLQ) for messages that fail processing after N retries. Use auto-scaling for analytics consumers based on queue depth metrics. Ensure idempotent message processing using event IDs to handle redelivery safely.
    HIGHSecurityAPI key management poses a significant risk: keys stored in plaintext in the database can be exfiltrated via SQL injection or insider threats. Additionally, the assumed rate limit of 100 req/min per API key at the gateway level may be insufficient to prevent enumeration attacks where an attacker iterates through short aliases to discover all active URLs.Store only hashed API keys (bcrypt or SHA-256 with salt) in the database, never plaintext. Implement alias enumeration protection: (1) Add jitter/randomness to alias generation so sequential guessing is ineffective. (2) Rate limit unauthenticated redirect requests by IP in addition to API key limits. (3) Consider requiring authentication for redirect analytics lookups. Implement API key rotation endpoints and automatic expiry. Log all key usage and alert on anomalous patterns.
    MEDIUMOperationalThe 90-day analytics retention policy with indefinite aggregated summaries creates operational risk: without a well-defined and tested data lifecycle management process, the PostgreSQL database will grow unboundedly. At scale (millions of redirects/day), raw analytics tables can reach terabytes within the retention window, causing query degradation and storage cost overruns.Implement PostgreSQL table partitioning on analytics tables by day or week (PARTITION BY RANGE on timestamp). Create an automated purge job (pg_cron or Kubernetes CronJob) that drops old partitions rather than running DELETE statements. Pre-aggregate analytics into summary tables (hourly/daily rollups) via scheduled jobs before raw data expires. Set storage quotas and alerting at 70%/90% thresholds. Test the purge job in staging with production-scale data volumes.
    MEDIUMScalabilityWith 3 Kubernetes replicas and a distributed counter for alias generation, the counter becomes a coordination bottleneck under high write throughput. A single Redis INCR counter serializes all URL creation requests, limiting write throughput to roughly the Redis command latency (~0.1ms = ~10k ops/sec theoretical max), which may be insufficient for burst traffic.Implement a range-based counter allocation strategy: each service instance pre-allocates a block of IDs (e.g., 1000 at a time) from Redis or a PostgreSQL sequence, then assigns them locally without network round-trips. This reduces counter contention by 1000x while maintaining global uniqueness. Alternatively, use a Snowflake-style ID generator that encodes timestamp + instance ID + sequence to eliminate the central coordinator entirely.
    HIGHSecurityJWT/OAuth2 tokens for user-facing operations introduce token replay and privilege escalation risks. If JWTs are long-lived or if token revocation is not implemented (JWTs are stateless by default), a compromised token remains valid until expiry. Additionally, without proper scope validation, a user token might be accepted for service-to-service API key endpoints.Set short JWT expiry (15 minutes) with refresh token rotation. Implement a token revocation list (Redis-backed blocklist) checked on every request for sensitive operations. Enforce strict audience (aud) and scope claims validation — user JWTs must not be accepted on service-to-service endpoints and vice versa. Use asymmetric signing (RS256/ES256) so the public key can be distributed without exposing signing capability. Rotate signing keys quarterly.

    Trade-offs

    • Counter-based vs hash-based alias generation: Counter-based (chosen) guarantees uniqueness and avoids collisions but requires a distributed coordination mechanism and leaks information about URL creation volume. Hash-based is stateless but requires collision handling and retry logic at scale.
    • Synchronous vs asynchronous analytics: Async via message queue (chosen) keeps redirect p99 latency low and decouples concerns, but introduces eventual consistency in analytics — dashboards may lag real-time by seconds to minutes and require additional infrastructure (Kafka/SQS, consumers, DLQ).
    • Redis + PostgreSQL dual-store vs single store: The dual-store approach (chosen) optimizes for redirect read performance (sub-millisecond from Redis) at the cost of operational complexity, cache invalidation logic, and the need to handle cache-DB consistency during URL updates or deletions.
    • API-only (no UI) for this phase: Reduces scope and delivery time but means analytics consumers must build their own tooling or wait for a future phase, potentially limiting adoption and making it harder to validate analytics correctness without dedicated tooling.
    • 90-day raw analytics retention: Balances storage cost against analytical flexibility. Shorter retention reduces storage but limits trend analysis; indefinite retention of aggregated summaries preserves high-level insights while bounding storage growth, at the cost of losing drill-down capability on older data.
    • API gateway rate limiting vs application-level rate limiting: Gateway-level (chosen) is simpler and protects all services uniformly, but is less flexible — per-user or per-URL-owner rate limits require application awareness. A hybrid approach would be more precise but adds complexity.
    • Kubernetes with 3 replicas minimum: Provides HA and rolling deployments without downtime, but requires careful handling of stateful concerns (counter coordination, cache warming) during pod restarts and scaling events. Stateless redirect pods scale easily; stateful components (Redis, PostgreSQL) require separate HA strategies.
