1. Requirement Analysis

Type: Ambiguous  |  Intent: Implement an LRU (Least Recently Used) caching mechanism for a production microservice deployment to improve performance and reduce redundant data fetching.

Functional Requirements

  1. Cache must evict the least recently used entry when the cache reaches its maximum capacity
  2. Cache must support O(1) average time complexity for both get and put operations
  3. Cache must support a configurable maximum capacity (item count or memory size)
  4. Cache must provide a get(key) operation that returns the cached value or a cache-miss indicator
  5. Cache must provide a put(key, value) operation that inserts or updates a cache entry
  6. Cache must support TTL (time-to-live) expiration per entry or globally
  7. Cache must expose metrics such as hit rate, miss rate, eviction count, and current size
  8. Cache must support cache invalidation by key or bulk invalidation
  9. Cache must be accessible across microservice instances (distributed or local per instance)

Non-Functional Requirements

  • Thread-safe implementation to handle concurrent reads and writes in a multi-threaded microservice environment
  • Low latency: cache operations must complete in sub-millisecond time for local cache or low single-digit milliseconds for distributed cache
  • High availability: cache layer must not become a single point of failure for the microservice
  • Scalability: cache must handle high throughput (thousands of requests per second) without degradation
  • Observability: cache must integrate with existing monitoring/tracing infrastructure (e.g., Prometheus, OpenTelemetry)
  • Memory efficiency: cache must not cause excessive memory pressure or GC pauses in the host process

  • ✅ A well-known library (e.g., Caffeine for JVM, functools.lru_cache or cachetools for Python, node-lru-cache for Node.js) is acceptable rather than a from-scratch implementation

2. Architecture Design

A two-tier caching architecture combining a high-performance in-process LRU cache (L1) backed by a distributed Redis cluster (L2) to serve cached data with sub-millisecond local latency and cross-instance consistency. The system is designed as a sidecar-compatible, non-blocking cache layer that degrades gracefully when the distributed backend is unavailable, ensuring microservice resilience. Metrics, TTL enforcement, and invalidation are first-class concerns integrated with Prometheus and OpenTelemetry.

    @field_validator("value")
    @classmethod
    def validate_value_size(cls, v: bytes) -> bytes:
        max_size = 1_048_576  # 1 MB default; overridden per namespace
        if len(v) > max_size:
            raise ValueError(f"Value size {len(v)} exceeds max {max_size} bytes")
        return v

    @model_validator(mode="after")
    def compute_size_and_expiry(self) -> "CacheEntry":
        """Auto-compute size_bytes and expires_at from ttl_ms."""
        if self.size_bytes == 0:
            self.size_bytes = len(self.value)
        if self.ttl_ms is not None and self.expires_at is None:
            self.expires_at = self.created_at + self.ttl_ms
        return self

    def is_expired(self) -> bool:
        """Check whether this entry has passed its TTL."""
        if self.expires_at is None:
            return False
        return int(time.time() * 1000) >= self.expires_at

    def remaining_ttl_ms(self) -> Optional[int]:
        """Return remaining TTL in milliseconds, or None if no TTL."""
        if self.expires_at is None:
            return None
        remaining = self.expires_at - int(time.time() * 1000)
        return max(0, remaining)

    model_config = {"arbitrary_types_allowed": True}

    test_lru_eviction_policy_under_capacity unit — Unit test: Verifies that the LRU eviction policy correctly evicts the least-recently-used entry when the L1 cache reaches its maximum capacity 
    import pytest
from collections import OrderedDict


class SimpleLRUCache:
    """
    Minimal LRU cache implementation for testing eviction policy.
    Mirrors the expected behavior of the production L1 cache.
    """
    def __init__(self, max_size: int):
        self.max_size = max_size
        self._store = OrderedDict()
        self.eviction_count = 0
        self.evicted_keys = []

    def get(self, key: str):
        if key not in self._store:
            return None
        self._store.move_to_end(key)  # Mark as recently used
        return self._store[key]

    def set(self, key: str, value, ttl: int = 300):
        if key in self._store:
            self._store.move_to_end(key)
        self._store[key] = {'value': value, 'ttl': ttl}
        if len(self._store) > self.max_size:
            evicted_key, _ = self._store.popitem(last=False)  # Remove LRU
            self.eviction_count += 1
            self.evicted_keys.append(evicted_key)

    def __len__(self):
        return len(self._store)

    def keys(self):
        return list(self._store.keys())


def test_lru_eviction_policy_under_capacity():
    """
    LRU cache with max_size=3 must:
    1. Hold up to max_size entries without eviction
    2. Evict the LRU entry when capacity is exceeded
    3. Promote accessed entries to MRU position
    4. Track eviction count accurately
    5. Never exceed max_size
    """
    cache = SimpleLRUCache(max_size=3)

    # Fill to capacity
    cache.set('key:A', 'value_A')
    cache.set('key:B', 'value_B')
    cache.set('key:C', 'value_C')

    assert len(cache) == 3, f'Cache should hold 3 entries, has {len(cache)}'
    assert cache.eviction_count == 0, (
        f'No evictions expected at capacity, got {cache.eviction_count}'
    )

    # Access key:A to make it MRU (key:B becomes LRU)
    result_a = cache.get('key:A')
    assert result_a is not None, 'key:A should be accessible'
    assert result_a['value'] == 'value_A', (
        f"Expected 'value_A', got '{result_a['value']}'"
    )

    # Add key:D — should evict key:B (LRU)
    cache.set('key:D', 'value_D')

    assert len(cache) == 3, (
        f'Cache should still have 3 entries after eviction, has {len(cache)}'
    )
    assert cache.eviction_count == 1, (
        f'Expected 1 eviction, got {cache.eviction_count}'
    )
    assert 'key:B' in cache.evicted_keys, (
        f'key:B should have been evicted (LRU), evicted: {cache.evicted_keys}'
    )

    # key:B should now be a miss
    assert cache.get('key:B') is None, (
        'key:B should be a cache miss after eviction'
    )

    # key:A, key:C, key:D should still be present
    assert cache.get('key:A') is not None, 'key:A should still be in cache'
    assert cache.get('key:C') is not None, 'key:C should still be in cache'
    assert cache.get('key:D') is not None, 'key:D should still be in cache'

    # Add two more entries — each should trigger one eviction
    cache.set('key:E', 'value_E')
    cache.set('key:F', 'value_F')

    assert cache.eviction_count == 3, (
        f'Expected 3 total evictions, got {cache.eviction_count}'
    )
    assert len(cache) == 3, (
        f'Cache should never exceed max_size=3, has {len(cache)}'
    )

    # Update existing key — should NOT cause eviction
    pre_eviction_count = cache.eviction_count
    existing_key = cache.keys()[0]
    cache.set(existing_key, 'updated_value')
    assert cache.eviction_count == pre_eviction_count, (
        'Updating an existing key should not trigger eviction'
    )
    assert len(cache) == 3, (
        'Updating existing key should not change cache size'
    )

    6. Risk Assessment & Validation

    Identified Risks

    SeverityCategoryDescriptionMitigation
    HIGHData IntegrityL1 cache coherence lag across instances: Redis Pub/Sub invalidation is fire-and-forget with no delivery guarantee. If a service instance misses an invalidation event (network partition, restart, subscriber lag), its L1 cache will serve stale data for the remainder of the TTL window. This is especially dangerous for user-sensitive or financial data where consistency is critical.Implement a hybrid invalidation strategy: (1) Set a short, bounded L1 TTL (e.g., 30s max) independent of L2 TTL so stale data self-heals. (2) Use Redis Streams instead of Pub/Sub for invalidation events to enable at-least-once delivery with consumer group acknowledgment. (3) On service startup, flush L1 entirely before subscribing to the invalidation channel to avoid serving pre-restart stale state. (4) For PII/financial namespaces, disable L1 caching entirely per the PII flag in the Configuration Store.
    CRITICALSecurityPII and sensitive data leakage via L2 Redis: The architecture flags sensitive keys to disable L2 caching, but this enforcement lives in the Cache Manager facade. A misconfigured namespace, a missing PII flag, or a bug in the serialization path could silently persist regulated data to Redis Cluster, which may not meet data residency or encryption-at-rest requirements. Redis persistence is disabled, but replicas and AOF snapshots during failover could still expose data.Implement a defense-in-depth approach: (1) Enforce PII namespace filtering at the key-generation layer before any Redis call, not just as a conditional branch. (2) Add a unit-tested allowlist of namespaces permitted to use L2; default-deny for unknown namespaces. (3) Enable Redis TLS (redis-py ssl=True, Lettuce SSL, ioredis tls:{}) for in-transit encryption. (4) Rotate Redis AUTH credentials via Vault or AWS Secrets Manager with zero-downtime rotation support. (5) Add an integration test that asserts PII-flagged keys are never written to Redis.
    HIGHAvailabilityCache stampede (thundering herd) on cold start or after cache flush: The Cache Warming preloader runs asynchronously and does not block readiness, meaning the service can receive production traffic before the cache is warm. Under high concurrency, hundreds of simultaneous cache misses for the same key will all reach the origin (DB or external API) simultaneously, potentially overwhelming the downstream system and causing cascading latency or failures.Implement probabilistic early expiration (PER) or a request-coalescing/mutex pattern: (1) Use a per-key async lock (e.g., Caffeine's AsyncLoadingCache, asyncio.Lock per key in Python, or a Redis SET NX lock) so only one request fetches from origin while others wait and reuse the result. (2) Add jitter to TTL values (±10-15%) to prevent synchronized mass expiration. (3) Implement a 'stale-while-revalidate' pattern: serve the expired entry while a background thread refreshes it. (4) Rate-limit the cache warmer to avoid it competing with live traffic on startup.
    HIGHPerformanceUnbounded memory growth in L1 cache under misconfiguration: The max-entry count bound is configurable, but if the optional max-memory-bytes limit is not set in containerized environments (Kubernetes pods with memory limits), a large average value size combined with a high entry count can cause the JVM/Python process to exceed its container memory limit, triggering OOM kills. Caffeine's weight-based eviction requires explicit weigher configuration.(1) Make max-memory-bytes a required configuration field (not optional) for containerized deployments, validated at startup with a fail-fast check. (2) Set the Caffeine weigher to measure serialized byte size of values, not just entry count. (3) Configure L1 max size to no more than 20% of the container's memory limit, enforced via a startup assertion. (4) Set JVM -XX:MaxRAMPercentage or Python memory profiling alerts. (5) Add a Prometheus alert on JVM heap usage > 80% correlated with cache size metrics.
    MEDIUMOperationalRedis SCAN-based bulk invalidation blocking production traffic: The Cache Invalidation Service uses SCAN+DEL for pattern-based bulk invalidation. On a large Redis keyspace (millions of keys), SCAN iterations are non-blocking individually but can generate thousands of DEL commands in rapid succession, causing Redis CPU spikes and latency increases for concurrent GET/SET operations from live traffic. This is compounded in Redis Cluster mode where SCAN must be run per shard.(1) Rate-limit bulk invalidation operations using a token bucket or sleep-between-cursor approach (e.g., 100ms pause every 1000 keys scanned). (2) Prefer key tagging via Redis Sets (store key references in a tag set, then SMEMBERS + DEL) over SCAN to reduce iteration overhead. (3) Schedule large bulk invalidations during low-traffic windows via a job scheduler. (4) Add a circuit breaker specifically for invalidation operations so a runaway SCAN does not trigger the main circuit breaker and degrade cache reads. (5) Monitor Redis latency percentiles (p99 > 5ms alert) during invalidation runs.
    HIGHData IntegritySerialization version mismatch causing deserialization failures or silent data corruption: The Cache Manager handles serialization/deserialization of cached values. When a microservice is deployed with a rolling update that changes a cached object's schema (added/removed fields, type changes), L2 Redis will contain entries serialized by the old version while new instances attempt to deserialize them with the new schema. This can cause runtime exceptions, silent null fields, or incorrect business logic.(1) Include a schema version or content hash in the cache key namespace (e.g., 'user-profile:v3:{id}') so old and new versions never collide. (2) Use schema-evolution-safe serialization formats (Protobuf with field numbering, Avro with schema registry, or JSON with explicit null handling) rather than Java serialization or pickle. (3) Implement a cache key versioning policy in the Configuration Store that increments on each deployment with schema changes. (4) Add a deserialization error handler in the Cache Manager that treats deserialization failures as cache misses (log + fetch from origin) rather than propagating exceptions.
    MEDIUMScalabilityRedis Cluster hot-key skew under high cardinality access patterns: If a small number of cache keys (e.g., a global configuration object or a viral content item) receive disproportionately high read traffic, all requests hash to the same Redis shard, creating a hot-key bottleneck that saturates that shard's CPU and network bandwidth. Redis Cluster's sharding does not automatically rebalance hot keys.(1) Implement local key replication for detected hot keys: replicate the value across N shards using a suffix (e.g., 'hot-key:{random 0-9}') and read from a random shard. (2) Rely on L1 cache as the primary defense—hot keys should almost always be served from L1 after the first miss. (3) Monitor per-shard command rate via Redis INFO commandstats and alert on shard imbalance > 3x average. (4) Use Redis replica reads (already planned) to distribute read load across replicas for the hot shard. (5) Consider a dedicated Redis instance for known global/hot-key namespaces.
    MEDIUMOperationalCircuit breaker miscalibration causing premature or delayed opening: The circuit breaker wrapping Redis calls uses thresholds for failure rate and latency. If thresholds are too sensitive, transient Redis hiccups (GC pause, network jitter) will open the circuit and force all traffic to origin, potentially overwhelming the DB. If too lenient, a degraded Redis will continue to receive traffic and add latency to every request before timing out.(1) Use a sliding-window count-based breaker (Resilience4j COUNT_BASED, 20-request minimum) rather than time-based to avoid opening on sparse traffic. (2) Set separate thresholds for L2 read failures (higher tolerance, fall back to origin) vs. L2 write failures (lower tolerance, writes can be dropped). (3) Implement a half-open probe with a single test request before fully closing the circuit. (4) Expose circuit breaker state (OPEN/CLOSED/HALF_OPEN) as a Prometheus gauge and alert on sustained OPEN state > 60 seconds. (5) Load-test circuit breaker behavior with chaos engineering (e.g., Toxiproxy simulating Redis latency spikes) before production deployment.

    Trade-offs

    • Two-tier (L1+L2) vs. single distributed cache: L1 adds sub-millisecond hit latency and Redis failure resilience but introduces per-instance cache coherence complexity and potential for stale reads between invalidation events. A single Redis-only cache would be simpler to reason about for consistency but would add 1-5ms network overhead on every cache hit and create a single point of failure.
    • TTL-based expiration vs. event-driven invalidation: TTL provides a simple, self-healing staleness bound but means data can be stale for up to TTL duration after a mutation. Event-driven invalidation (Pub/Sub) provides near-real-time consistency but adds operational complexity and has no delivery guarantee. The architecture uses both, which is correct but requires careful TTL sizing to bound worst-case staleness when invalidation events are missed.
    • LRU eviction (Caffeine W-TinyLFU) vs. pure LRU: Caffeine's W-TinyLFU provides better hit rates than strict LRU for skewed access patterns (Zipf distribution, common in production) by protecting frequently accessed items from one-time scan pollution. The trade-off is slightly higher CPU overhead for frequency tracking and less predictable eviction order, which can complicate debugging cache behavior.
    • Async cache warming vs. blocking readiness: Running the preloader asynchronously allows faster service startup and avoids blocking health checks, but means the service accepts traffic in a cold-cache state. This trades startup latency for potential thundering herd risk during the warm-up window. A hybrid approach (warm top-N keys synchronously, rest async) would reduce this risk at the cost of slower startup.
    • Write-through vs. write-around policy: Write-through keeps cache and origin in sync on writes but doubles write latency and can pollute the cache with infrequently re-read data. Write-around avoids cache pollution but means the next read after a write will always be a cache miss. The architecture supports both via policy selection, which is correct but requires per-namespace policy governance to avoid inconsistent behavior.
    • Shared library distribution vs. sidecar proxy: Embedding the Cache Manager as a shared library (Maven/PyPI/npm) gives low-latency access and language-native integration but creates a library versioning and upgrade coordination problem across all consuming services. A sidecar proxy (e.g., Envoy with cache filter) would centralize cache logic but add network hop overhead and operational complexity.
    • Redis persistence disabled vs. enabled: Disabling persistence treats Redis purely as a cache tier, simplifying operations and avoiding disk I/O overhead. However, after a Redis Cluster restart or failover, the entire L2 cache is cold, causing a thundering herd on the origin. Enabling RDB snapshots with a short interval would reduce cold-start impact at the cost of disk I/O and slightly increased memory usage.
